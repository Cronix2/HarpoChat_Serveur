# P5 — Mesh Sphinx multi-nœuds (M2) Implementation Plan

**Goal:** Packets cross several nodes: phone → gateway → mix → mailbox, replies mailbox → mix → gateway → phone, with sender-chosen exponential delays and adaptive path length. An integration test on 5 in-process nodes passes, and the mailbox never sees the recipient's connection (spec §15, M2).

**Architecture:** `harpochat-core` gains `path` (pure route selection over verified nodes, adaptive 1 → 3 mix layers, diversity rules of spec §4.3, exponential delays from caller-supplied randomness). `harpochat-server` gains `peers` (node-to-node links: lazily dialled with `net::connect` using the node identity and the expected peer id, one writer queue per peer, inbound node links recognised by their `NodeAuth`), and the router forwards to peers instead of dropping. Peer discovery in P5 is static: `[[peers]]` in the config (id + endpoint), descriptors learnt by `DirectoryReq` over the link; gossip and sponsorship replace this in P7.

**Tech Stack:** existing crates only.

**Spec:** §4.3 (sélection de chemins), §6.1–6.2, §13; design §5.3, §5.7.

## Global Constraints

- A route never contains the same node twice (spec §4.3). Minimum 3 distinct nodes when the mesh has ≥ 3 nodes; a 1- or 2-node mesh uses what exists (dev/test only, documented).
- Mixing layers: `< 12` usable nodes → 1 mix; `≥ 12` → 3 mixes, one per layer 0/1/2 (spec §6.1, §13).
- Delays: exponential, mean `100 ms` default, capped at `sphinx::MAX_DELAY_MS`; zero on the gateway hop and the final hop (only mixes delay, spec §6.2).
- Diversity: avoid two nodes with the same direct sponsor, then two nodes sharing an IPv4 /16 (only when endpoints are IP literals), relaxing in that order when the mesh is too small; never relax "distinct nodes".
- Node links carry Sphinx frames only from authenticated nodes (`peer.node_id` known **and** present in the node's verified peer set); phones cannot inject `Forward` traffic addressed as a node.
- No per-packet logs; aggregated counters only.
- Conventional commits; branch `feat/p5-mesh`.

## Review Focus

1. **A mesh of 5 nodes where one is down** → routes avoid it once the link fails; packets to it are dropped and counted, nothing hangs (Task 4, `unreachable_peer_drops_without_blocking`).
2. **All nodes sponsored by the same root** (typical small mesh) → sponsor diversity is relaxed, routes still have distinct nodes (Task 1, `small_mesh_relaxes_diversity`).
3. **Delay sampling with an RNG returning extremes (0.0 / ~1.0)** → finite delays within the cap (Task 1, `exponential_delays_bounded`).
4. **A phone that sends a Sphinx packet whose first hop is some other node** → the gateway forwards it (that is normal Loopix behaviour) but a phone link can never make the node accept traffic "from a node" (Task 3, `phone_link_is_not_a_node_link`).
5. **Gateway with no phone for a returning SURB** → dropped, counted (already covered in P4; re-run in Task 5).

### Task 1: Core — path selection and delays

**Files:** Create `crates/harpochat-core/src/path.rs`; modify `lib.rs`.

**Interfaces — Produces:**
- `pub const SMALL_MESH_LIMIT: usize = 12; pub const DEFAULT_MEAN_DELAY_MS: u64 = 100;`
- `pub fn exponential_delay_ms(mean_ms: u64, uniform: f64) -> u64` — `-mean · ln(1 − u)` with `u` clamped to `[0, 1 − 1e-9]`, result capped at `sphinx::MAX_DELAY_MS`.
- `pub struct Candidate { pub hop: Hop, pub roles: Vec<Role>, pub layer: u8, pub sponsor: Option<[u8; 32]>, pub ipv4_16: Option<[u8; 2]> }` with `From<&VerifiedNode>` (`ipv4_16` from the first endpoint whose host is an IPv4 literal).
- `pub struct Route { pub hops: Vec<Hop>, pub delays_ms: Vec<u64> }`.
- `pub fn forward_route(nodes: &[Candidate], gateway: &[u8; 32], mailbox: &[u8; 32], pick: &mut dyn FnMut(usize) -> usize, uniform: &mut dyn FnMut() -> f64, mean_ms: u64) -> Result<Route>` — `gateway → mix… → mailbox`; mix count 1 or 3 per `SMALL_MESH_LIMIT` over nodes having role `Mix`; layered when 3 (`layer == i`); excludes gateway and mailbox from mixes; diversity rules with relaxation order; `pick(n)` returns an index `< n` (caller's RNG); delays `[0, mix…, 0]`. `Untrusted` if gateway or mailbox unknown; `Malformed` if no mix can be found distinct from both (mesh of < 3 nodes: route `gateway → mailbox` if distinct, or `[gateway]` if equal).
- `pub fn reply_route(…same…, gateway, …)` — `mix… → gateway` for SURBs (mailbox sends; it is not part of the SURB route).
- **Mailbox placement (spec gap, deviation E14):** `pub fn mailbox_nodes(mailbox_id: &[u8; 32], nodes: &[Candidate], n: usize) -> Vec<[u8; 32]>` — rendezvous hashing: nodes with role `Mailbox`, ranked by `h_domain("harpo-mbx-place", [mailbox_id, id_pub])` descending, first `n`. `MAILBOX_REPLICAS = 3`. A route may never end at its own gateway (the gateway would see both the phone and the mailbox id), so the sender PUTs to every replica that is not its gateway (≥ 2) and the recipient FETCHes every replica that is not its gateway (≥ 2): the two sets always intersect. A small directory difference moves at most one replica.
- Tests add: `mailbox_placement_is_deterministic`, `placement_changes_little_when_a_node_leaves` (removing a non-selected node changes nothing; removing the first moves only it).

- [ ] Tests: `three_node_route_shape`, `twelve_nodes_use_three_layers`, `never_repeats_a_node` (property: 200 random picks over 5 nodes), `prefers_distinct_sponsors`, `small_mesh_relaxes_diversity`, `avoids_shared_ipv4_16`, `exponential_delays_bounded` (u = 0 → 0, u = 1 → ≤ cap, mean over 10 000 samples within 10 % of mean), `gateway_and_final_hops_have_zero_delay`, `unknown_mailbox_rejected`.

### Task 2: Config `[[peers]]` and peer table

**Files:** modify `crates/harpochat-server/src/config.rs`; create `src/peers.rs`.

**Interfaces — Produces:**
- `Config.peers: Vec<PeerConfig { id_pub: String, endpoint: String /* "host:port" or wss:// URL */ }>` validated like roots (hex id, endpoint parseable to `SocketAddr` after optional `wss://` strip; DNS names resolved at dial time).
- `pub struct Peers` — `new(own_id, keys: NodeKeys, configured: Vec<(id, endpoint)>)`; `known(&self) -> Vec<[u8; 32]>`; `addr_to_id(&self, node_addr: &[u8; 32]) -> Option<[u8; 32]>` (via `descriptor::node_address`); `send(&self, node_addr: &[u8; 32], packet: Vec<u8>) -> bool` — non-blocking enqueue on the peer's writer; lazily spawns a dialler task (`net::connect(addr, &keys.noise, Some(&keys.identity), Some(peer_id))`) with exponential back-off (1 s → 60 s); queue 1 024 packets, overflow → dropped.
- `pub fn accept_node_link(&self, peer_id, writer)` — an inbound authenticated node link also becomes the writer for that peer (no duplicate dial).

### Task 3: Router forwarding and link roles

**Files:** modify `src/router.rs`, `src/server.rs`.

- [ ] Router: `Forward` to `own_addr` → local (as today); to a known peer address → `peers.send` after the delay; unknown → drop. Replies from the mailbox: `use_surb` → first hop may be a peer → same path.
- [ ] Server: after `net::accept`, if `peer.node_id` is `Some(id)` **and** `id ∈ peers.known()`, the link is a node link: register it with `peers.accept_node_link`, accept only `Sphinx`, `DirectoryReq`, `Padding`; `RegisterInbox` from a node link is ignored. Otherwise it is a phone link (as in P4).
- [ ] Directory: a node answers `DirectoryReq` with itself **plus** the descriptors it learnt from its peers (each peer's own signed descriptor obtained by a `DirectoryReq` on the node link at connect time, stored with an empty chain when the peer is a configured root; entries that do not verify are not relayed).
- [ ] Tests (`router.rs`, `server.rs`): `forward_to_peer_after_delay`, `phone_link_is_not_a_node_link` (a phone presenting no identity cannot register as a peer; a node not in `[[peers]]` is treated as a phone), `directory_includes_peers`.
